## Recovered collector failure topology

serializeToDisk0xdf2c8 cleans existing archives and attempts archive-directory setup before copying actions/log state under the state lock. Archive setup failure exits through its separate error return. The source retains local action/log arrays and releases the lock; it does not clear the collector's original action queue. It then appends generated summary, optional crash/log/process/simulator actions to its local list. Those generated actions and their command execution remain unimplemented/unexecuted in this wake.

The action loop0xdf7b0..0xdf8b0 calls each action's serialize witness sequentially. On failure it retains the Swift error, appends it to the local error array, releases/reset the temporary error register and proceeds to the next action. Success also proceeds. Thus one bad file is not a batch abort, and error order follows action encounter order. There is no automatic retry or queue consumption here.

If errors exist, source maps them through a string-interpolation helper, joins with two LF, applies its fixed escaped-newline replacement and writes SerializationErrors.txt atomically as UTF8. A failure of that report write is released/cleared. The createZip flag independently gates writeZipArchive, whose error is returned separately. Native archive setup/ZIP failures are therefore distinct from non-fatal action errors and discarded report-write errors. These are source observations; the batch API added here does not claim to implement cleanup, generated actions, error-string formatting/report output or ZIP.
