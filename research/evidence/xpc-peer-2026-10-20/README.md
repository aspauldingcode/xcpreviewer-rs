# Native XPC reply decoding across owned processes

This advances the prior generic fileport feasibility boundary to actual native BSActionResponse serialization, kernel transfer and native BSActionResponder decoding in separate owned processes. Two native cases and two portable-body cases preserve distinct and aliased FD attachments; an intentional wrong-order case fails semantic matching while remaining syntactically accepted. No Xcode process, built-in MCP or retained private bridge is used. This is scoped BaseBoard/libxpc transport evidence, not actual Canvas lifecycle correlation or full protocol parity.

Parent and child each construct native actions and responders using the previously verified Objective-C methods with exact runtime type checks through NSInvocation. Original interposition is linked only into newly built owned helpers. On the parent's first native sendResponse:, the research hook does not send that response body. Instead it moves that owned remote send-once right in an SDK mach_msg_port_descriptor_t to the child over an audit-verified random rendezvous. The successful capability-transfer result is returned to that intercepted parent sender. The recorded parent dummy send is therefore not treated as an actual payload send or compared as one. No private C/Swift ABI is invented or invoked.

Child receives the endpoint as PORT_SEND_ONCE, builds its own real native BSActionResponse containing owned xpc_fd objects, and redirects that owned native send to the received endpoint. Its original unused destination right is explicitly deallocated: native send-once notification message71 produces an error/no-payload callback in the child. This separate cancellation observation is retained and never counted as another successful response. The child native serializer and parent native decoder execute actual libxpc call sites. Native receive audit trailer PID matches the exact fork/exec child, whose PID differs from the parent. Ready/endpoint exchange also verifies audit peer identity.

Each child's original pipe writer and Unix read descriptor close before serialization. Native sender descriptor-number reuse does not merge distinct pipe resources. In the distinct cases, parent gets two23-byte expected contents; in alias cases, the first read consumes23 bytes and the second sees EOF because both imported descriptors share the same open-file position. Parent callback first reaps the exact child successfully, then xpc_fd_dup and content reads execute. Explicit receipt state records this ordering. Native XPC decoding/import of attachment objects may occur before peer exit; only descriptor duplication and reads are claimed after exit. Parent queue barrier and finite callback observation show one valid parent callback. Parent then verifies temporary rendezvous removal. No final kernel reclamation or universal no-later-effect claim follows.

The current original Rust reencode-xpc-attachments CLI is rebuilt and given each captured child XPC body. Canonical sorting emits descriptor_order[1,0]. An owned native research adapter permutes only SDK-validated original COPY_SEND attachment descriptors and substitutes the portable body while preserving the actual endpoint. Parent's native decoder accepts the result and preserves both distinct and alias semantics. Substituting the same canonical body with identity descriptor order is syntactically accepted but swaps resources and fails the expected-content matcher. This discriminates valid bytes from correct capability binding across actual processes. Portable codec and CLI still only describe ordinals; this research adapter is not a portable OS capability backend.

Both sender and receiver descriptor name relationships are independently checked for alias/distinct cases; no cross-task name equality or global identity is assumed.
