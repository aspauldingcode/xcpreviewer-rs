# Scalar normalization conformance in WebAssembly and JavaScript

This is research verification tooling for the newly measured public Quartz arithmetic boundary. It is not a renderer or a production/clean-room implementation handoff. A single owned Node/V8 process exercised a minimal81-byte WebAssembly module and JavaScript Math.fround paths, under the exclusive controller lock, fixed09:35UTC deadline, one-shot start marker and10second outer bound. Actual process exit is zero; no UI or native Apple API was called during this acquisition.

The module exports only multiplyBits and divideBits, each taking an integer byte and returning reinterpreted Float32 bits. Its sections are type, function, export and code only. It has no imports, memory, start or custom section. The harness checks that shape before instantiation. Source generation and module bytes are pinned. The module uses unsigned integer-to-Float32 conversion followed by explicit reciprocal multiplication or division, not a language compiler's inferred optimization.

Four paths generate the same independently prescribed test pattern: WASM reciprocal multiplication/division and JavaScript fround multiplication/division. The JavaScript host constructs the comparison buffers; this does not exercise WASM linear-memory rendering or a frame ABI. Every byte of four16,384-byte buffers matches both independent Python expectations and the separately sealed public Quartz byte-input/Float32-input routes. Total65,536 bytes includes768 row-padding and15,616 unused-tail bytes. Multiplication and division remain discriminated by1,152 opposite-expression bytes per buffer.

Five invalid host byte inputs reject before scalar dispatch;9,216 valid scalar calls execute. This validation belongs to the trusted test harness. The raw exported WASM functions are not general domain validators. Three synthetic admission methods pass normally and under optimization, covering rehashed pixel/padding/tail corruption and module/import/memory-section/nested-number/dispatch/domain/platform-claim/exit faults. Synthetic receipts are modeled controls, not extra executions.

Node24.19.0 with V8 13.6.233.17-node.51 on Darwin/arm64 is the only measured runtime/host. JavaScript and WASM are separate arithmetic paths in that same engine, not two independent runtimes. No second runtime or non-Apple OS is qualified. PATH lookups did not find wasmtime/wasmer/wat2wasm/wasm-tools; this does not establish global absence or preclude a public JavaScriptCore framework probe. No package or service was installed or purchased.

The separate verifier reviewed the module opcodes, source/pins, layout expectations, scope and one-shot gate before execution. No production repository code was changed. No new shipped-artifact analysis was needed: this is an owned source/module conformance test, not reverse engineering of a runtime implementation. The WASM bytes here are generated owned test code; no Apple executable or private dump is included.

Frozen replay with `python3 -B verify-frozen.py` or `python3 -O -B verify-frozen.py` validates the recorded execution, module provenance and all bytes against the separately pinned native oracle. It never reruns the engine or native fixture. The execution wrapper retains its original deadline and start marker.
