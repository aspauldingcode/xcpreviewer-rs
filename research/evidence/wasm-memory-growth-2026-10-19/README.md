# Owned non-browser WASM memory growth and stale host views

One bounded Node/V8 assay confirms a resource-identity distinction relevant to a future portable frame host: successful `memory.grow(0)` leaves the memory byte length unchanged while detaching cached ArrayBuffer/DataView/Uint8Array views. Successful growth through the WASM instruction also detaches prior views while preserving old memory and zero-initializing the added page. Growth beyond the declared maximum behaves differently: the JavaScript API throws RangeError, the WASM instruction returns -1, and both retain the current buffer and usable view. These are measured behaviors of one Node/V8 runtime on Darwin arm64, not browser, second-engine, other-OS, native Canvas or product acceptance.

The owned module is 80 bytes, SHA256 `970468fb9b02b07bd628c530877571db3d2ca614f73e8498b6fdd40455b3c0c6`. It has type/function/memory/export/code sections, one memory with minimum one and maximum two 64-KiB pages, no imports/start/data/custom sections, and exports `memory`, `store8` and `grow`. The C/Swift compiler and Apple frameworks are not used. `build.py` constructs the declared bytecode; the runtime validates it and checks its import/export shape before instantiation. This module is original research code and contains no shipped Apple bytes.

Five snapshots compare every byte against independent Python arrays: initial one-page memory, successful JavaScript zero growth, successful WASM one-page growth, failed JavaScript growth, failed WASM growth. The initial first-page pattern uses five 17-pixel byte rows at 96-byte stride, with 68 active bytes and 28 sentinel padding bytes per row. Explicit WASM stores mark offsets 0, 1, 65,539, 2 and 3 across the stages. Each snapshot preserves the complete first-page allocation except those predeclared markers. Each two-page snapshot has a zero-filled second page except its explicit marker. Across all snapshots, 524,288 bytes match: 700 row-padding bytes, 325,280 first-page tail bytes and 196,605 new-page zero bytes are included in the full comparison. This is a byte-pattern fixture, not a rendered image or a claimed pixel format.

After each successful growth, the old buffer and typed array have byteLength zero; old DataView reads throw TypeError; old typed-array reads return undefined; an attempted stale typed-array write has no effect on current memory. A new view sees the preserved prefix and the subsequent WASM store. After each failed growth the buffer identity and 131,072-byte view remain intact, and subsequent stores update the predicted bytes. Comparing only byte length would miss the successful zero-growth identity change. These observations motivate testing explicit view reacquisition in a portable ABI design, but no product policy or native frame-generation semantics are implemented here. Physical memory reclamation and shared-memory behavior are unmeasured.

Execution uses the exclusive controller lock, reviewed source pins, a one-shot marker, ten-second subprocess timeout and fixed 2026-10-19 17:00 UTC deadline with a twenty-second reserve. There was one fixture invocation; no retry. A separate bounded identity-only Node invocation is recorded before it. The reviewed synchronous fixture imports only local filesystem/crypto/URL helpers, starts no child process, accesses no network and uses no UI API. Successful admission requires actual subprocess exit zero and wait completion before the fixed deadline. This establishes controlled root completion; it does not claim arbitrary descendant or unseen-process quiescence.

The actual runtime is Node24.19.0 / V8 13.6.233.17-node.51, Darwin arm64. Its executable SHA256 is `768d7cb3d8a404059b095085b2a3803bcb1c8965e0b8eb95fc453bad9196974e`; REA6.2.0 matched and closed that arm64 artifact before execution. The runtime binary is not published. The runtime/host identity and exact source/module pins are retained. REA does not establish the lifecycle observations by static inspection: the controlled execution and captured bytes/events do.

Four synthetic methods and three recorded-evidence methods pass normally and with Python optimization. Rehashed active bytes, row padding, final tail bytes and added-page zeros reject. Altered view identity/error observations, Boolean terminal/length fields, incorrect runtime binding, paths, output inventory and late completion reject. The pinned strict JSON reader rejects duplicate/non-finite data. Frozen replay validates source/seal/output and Python tests only; it never invokes Node or instantiates the module again.
