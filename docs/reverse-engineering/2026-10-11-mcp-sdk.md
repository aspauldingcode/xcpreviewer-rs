# Official SDK client against the finite preview server

On 2026-10-11, the official `@modelcontextprotocol/client` 2.3.1 client and
`StdioClientTransport` accepted the owned prototype through an explicitly selected
legacy initialization handshake, tool discovery, finite source edits, rejection,
recovery and close. This is measured interoperability for the server's
2025-11-25 subset. The SDK's current 2026-07-28 modern negotiation, broad MCP
conformance, arbitrary SwiftUI, native Canvas transport and delivery acceptance
remain open. Both milestones remain open.

The official [TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk)
now publishes separate v2 client/server packages. The installed package README,
public declarations and implementation establish `versionNegotiation.mode:
'legacy'` as the appropriate explicit choice for this 2025-era server. No modern
probe sibling was launched. The free pinned package and its 12 dependencies were
installed only under a new temporary prefix with lifecycle scripts, funding and
audit requests disabled; no repository dependency or global install changed.
The lockfile retains registry integrity values. All 1,108 installed file hashes
were rechecked after the control. SDK package bytes stay local; the public
package can be restored using the retained lockfile.

An owned Python supervisor passed stdin/stdout/stderr through to the actual Node
server and retained its actual child wait status. The SDK used its actual stdio
transport; the public transport callback tap recorded messages without rewriting
requests or responses. This tests SDK interoperability across a supervisor,
not a direct unwrapped process launch. Each request had a timeout; the outer
control deadline was 35 seconds and the supervisor wait deadline was 12 seconds.
The server's existing ten-second lifetime and five-second build limit remained.

Two owned server sessions returned wait 0. The edit session produced three fresh
Rust modules, rejected an unsupported edit with actual CLI wait 2 while retaining
the prior frame, recovered, closed explicitly, returned a null frame after close,
and reported a failed restart through the generic `isError` tool result. The
second session produced one fresh module and closed through SDK transport EOF
without calling preview_close. Both ended with zero recorded workers/timers,
closed source loops and no retained frame. This is observed owned cleanup, not
arbitrary uncooperative subprocess or native resource reclamation acceptance.

The independent Python reader correlates all 17 responses with SDK results and
retained lifecycle files, checks actual server/CLI waits, compiler/source receipt
pins and all 81,920 frame allocation bytes including row padding and unused tail.
Four fresh V8 instances independently instantiate the saved modules and compare
complete allocations with the finite Python expectation. Three resealed SDK
version, wait-status and correlated padding-byte corruptions must fail. The
isolated candidate archive passes 87 Python tests and seven Rust tests.

Three harness/prediction failures remain retained. First, an incorrect config
replacement lost the observer object and referenced an absent CLI. Second, the
predicted post-close error conflicted with the handler's null frame result, while
the CLI was still absent. Third, an exit-0 protocol-only run had zero successful
builds: inspection rejected it as frame evidence. The final control freezes the
committed Rust CLI into the runtime, preserves the verified observer config and
requires non-null revision-1 startup frames. No failing deadline was increased.
The complete unsuccessful local directories remain excluded from publication;
compact failed scripts, configs, lifecycle/wait results and fingerprints are
sealed with the final evidence.
