A new owned peer exits0 after writing a deterministic eight-byte payload. Both controls use the same pinned public observer behind a0.2-second owned delay proxy, so the direct parent can observe the already-finished peer during snapshot validation. The original anchor body remains hash-pinned and unchanged. Its actual target Popen polls and real monotonic clock return values are recorded in the same supervisor process.

The baseline observes terminal wait0 before its one-second deadline and resolves normally. The changed control adds one explicitly injected scheduling delay between that terminal observation and the subsequent deadline clock call. The delay sleeps until50 milliseconds after the actual deadline; the clock then returns its real current value. No poll status or clock value is fabricated. The already-completed peer still has actual wait0 and drained receipt, but the anchor now records failure `deadline`; the production client retains the corresponding deadline error. Thus this owned fault-injection control demonstrates that post-completion observer scheduling can change the original deadline classification despite a terminal result already observed before the deadline.

This is not evidence that the historical compiler deadline arose from that mechanism, nor native Canvas timing or a universal timeout-policy verdict. It establishes a scoped source/owned-runtime boundary for reviewing a completion guard. Production timeout policy is unchanged. Both native producer assertions pass because the original reclassification is the prediction; the delayed client error remains in its result record.
