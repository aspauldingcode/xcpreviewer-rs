# Typed retirement probe and owning-parent counterexample

Added a separate read-only public libproc helper, `OwnedProcessRetirement.c`, and explicit Python `RetirementObserver`. The helper queries only supplied PID/birth pairs twice, reports `live`, `retired`, `reused` or `unavailable`, and never fabricates an executable path. The adapter validates complete bounded inventories and birth/state consistency, including integer types, and applies a two-second subprocess deadline. No compiler witness integration or default observer replacement is enabled.

The native prediction was that same-birth BSD process information would reveal an unreaped zombie even when the prior path-based helper omitted it. The owned waitid/waitpid fixture falsifies that prediction: the new helper reports `live` before exit and `unavailable` both during independently witnessed unreaped exit42 and after reap42. A wrong expected birth correctly produces `reused` while the real child is live; that is a controlled birth-mismatch check, not an actual PID-reuse claim.

A second discriminating control moves `proc_pidinfo(PROC_PIDTBSDINFO)` into the owning fixture parent itself. Live information returns the full136bytes, matching the same child birth and PID. After typed public `waitid(..., WEXITED|WNOWAIT)` reports child exit42, the owning parent's direct query returns0bytes. Its post-waitpid query also returns0bytes. Thus changing caller ownership does not recover BSD zombie visibility in this measured environment. This directly establishes a missing BSD-info result; the earlier suggested path-query mechanism was only a possible source explanation and cannot alone explain these measurements. No protection change or permission workaround was attempted.
